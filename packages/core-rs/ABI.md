# ardia_core C ABI

`include/ardia_core.h` is generated by cbindgen (`ARDIA_WRITE_HEADER=1 cargo test -p ardia-ffi --test header`) and
carries no comments, so its rules live here. C++ can include it directly: it has its own `extern "C"` guard. The
shared and static libraries' externally visible definitions are exactly the 15 C functions the header declares, plus
Rust's own mangled internals, and none of them names a fixture or a nonce, in every build configuration
(`tests/check_exports.py` reads the external definitions; local symbols aren't checked).

## What the caller must guarantee

The library can't tell a valid pointer from a dangling one. Undefined behavior comes only from an invalid pointer or
range, never from a value the library checks (next section):

- Every input `(pointer, length)` with a non-zero length points to `length` bytes that stay readable and unchanged
  for the whole call.
- Every non-`NULL` output slot (`ardia_buf *` or `ardia_sync_keys **`) points to aligned, readable and writable memory
  that nothing else touches during the call. Pass it empty (`{NULL, 0}` for a buffer, `NULL` for a key) to receive
  a result. A valid slot that isn't empty is not undefined behavior; it is refused with
  `ARDIA_STATUS_OUTPUT_IN_USE`.
- A buffer the library filled keeps its `ptr` and `len` unchanged until it goes back to `ardia_buf_free`, and goes back
  exactly once.
- A key handle comes from `ardia_sync_keys_new` and isn't used after `ardia_sync_keys_free`. Nothing else may use it
  while it is being freed.

## What the library checks

Only nulls, lengths and contents. Nothing more:

- A `NULL` input pointer with length 0 is an empty input. A `NULL` input pointer with a non-zero length, a `NULL` key
  or a `NULL` output slot returns `ARDIA_STATUS_INVALID_ARGUMENT`.
- A variable-length input over its cap (`ARDIA_MAX_*`) returns `ARDIA_STATUS_TOO_LARGE` before the pointer is read,
  so the cap wins over a `NULL` pointer: an over-cap length with a `NULL` pointer returns `ARDIA_STATUS_TOO_LARGE`.
- The caps are there to refuse a wrong length, not to limit real data. A vault payload may be up to 1 GiB
  (`ARDIA_MAX_PAYLOAD_BYTES`) and a sealed file that much plus 4 KiB, because the Swift that wrote most vaults had no
  cap and sync's checkpoint holds every scope in one file. A password, its origin and its username may each be that
  large too (`ARDIA_MAX_PASSWORD_FIELD_BYTES`), and a sealed password half as much again, since Swift sealed and
  opened passwords of any length. Scopes and file ids may be up to 64 KiB (`ARDIA_MAX_LABEL_BYTES`). A caller that can't show the user an error must still handle `ARDIA_STATUS_TOO_LARGE`:
  every refusal is a status, never an abort.
- Entropy is a fixed-size input: exactly `ARDIA_ENTROPY_BYTES`. Any other length, shorter or longer, returns
  `ARDIA_STATUS_INVALID_ARGUMENT` in both `ardia_sync_keys_new` and `ardia_phrase_from_entropy`.
- Text inputs that aren't UTF-8 return `ARDIA_STATUS_INVALID_ARGUMENT`.
- A valid output slot that isn't empty returns `ARDIA_STATUS_OUTPUT_IN_USE`, and the slot is left as it was, so a
  held buffer or key is never lost.

## Results

- Every call returns an `ardia_status`. `ARDIA_STATUS_OK` is the only success.
- On `ARDIA_STATUS_OK` the buffer holds the result. A result can be empty, and then the buffer stays `{NULL, 0}`. With any
  other status, except `ARDIA_STATUS_OUTPUT_IN_USE` or a `NULL` slot, it holds a JSON error: `{"code": "..."}`, plus
  `count` for `wordCount` and `index` (0-based word position) for `unknownWord`. Error JSON never contains phrase
  words, passwords or payloads; show the user's own input highlighted at `index` instead.
- Secret results (opened payloads, passwords, entropy, phrases) are plain bytes, never JSON. Copy out what you need,
  then free the buffer.
- `ardia_buf_free(&buf)` zeroes the bytes (with `memset_s` on Apple platforms, which the compiler may not remove, and
  with `zeroize`'s volatile writes elsewhere), frees them and resets the slot to `{NULL, 0}`. Freeing a reset slot or
  passing `NULL` does nothing. Freeing another copy of a buffer that was already freed is a double free.
- `ardia_sync_keys_new` writes a new handle that owns the derived keys and zeroes them when freed. A handle never
  changes after it's made, so threads may share it, but its free must be synchronized with every user.

## Runtime

The library keeps no globals and starts no threads. It reads no files. The only system call it makes is asking the
OS for random bytes, in `ardia_sync_seal`, `ardia_sync_new_file_id` and `ardia_phrase_generate_entropy`. A panic aborts
the process in release builds.

If the OS can't supply random bytes, what happens depends on the crypto backend:
- RustCrypto, used in cargo builds, returns `ARDIA_STATUS_RANDOM`.
- BoringSSL, used in Chromium's GN build, aborts the process. Its CSPRNG treats an entropy failure as fatal, as the rest
  of Chromium does.

## Nonces

Files and local state are sealed only with nonces drawn from the crypto backend's `fill_random`. In every shipped
build that backend is the OS. Passwords are sealed with their HMAC-derived deterministic nonce. No function in
`ardia-sync-core` or `ardia-ffi` takes a nonce. To reproduce the committed fixed-nonce vectors, the test crate
`ardia-sync-vectors` builds `SyncKeysWith<FixtureCrypto>`, a test-only backend that wraps the build's selected backend
and returns the fixture's nonce from `fill_random`, and then calls the normal `seal`. The selected backend is RustCrypto
under cargo and BoringSSL in Chromium's GN build.

## Reading what other platforms wrote

Password reads follow Swift exactly, because Swift wrote most existing vaults. Base64 decodes like Foundation's
`Data(base64Encoded:)`: extra trailing `=` are accepted, and whitespace and missing padding are not. One leading U+FEFF
is dropped from an opened password. Writes stay canonical. `tests/password-read-cases.json` and
`tests/phrase-cases.json` record where Linux, Windows and Kotlin read differently today.

## Update manifests: `ardia_update`

`include/ardia_update.h` (`ARDIA_WRITE_HEADER=1 cargo test -p ardia-update-ffi --test header`) is a second, separate
library, `libardia_update`, built by `crates/ardia-update-ffi` over `crates/ardia-update-core`. It exports exactly the 5
functions its header declares, every name starts with `ardia_update`, and both headers can be included in one
translation unit. It stays its own library, outside `ardia_core.h`, `BUILD.gn` and `ardia-ffi`, until a platform calls
it: the Linux engine copies those three, so adding to them moves the Linux engine key. The cutover that wires the
Linux or Windows updater to it folds it into `ardia_core` (one `use` in `ardia-ffi` and the GN targets). Until then,
don't link both cargo static libraries into one binary: each carries Rust's standard library.

It verifies the signed Linux self-update manifest (`ardia-linux-update 1`, see `docs/linux-port.md` › Signed
manifest) and compares versions and channels, with the rules of the root helper `scripts/linux/ardia-update`:

- `ardia_update_verify_linux` checks, in this order: the kind (`ARDIA_UPDATE_KIND_*`) and the 32-byte public key
  (`ARDIA_UPDATE_STATUS_INVALID_ARGUMENT`), the requested and installed versions (`VERSION`), the manifest's size,
  at most 4096 bytes (`TOO_LARGE`), the raw 64-byte Ed25519 signature over the manifest's exact bytes (`SIGNATURE`; any
  other length is a bad signature and isn't read), the strict canonical parse (`MANIFEST`), that the manifest is for the
  requested version (`MANIFEST`), that it is newer than the installed one (`NOT_NEWER`), and that it has a line for this
  kind (`KIND`). On `OK` it writes the package's size and sha256; on any other status it zeroes the output.
- Versions are `<major>.<minor>.<patch>` or `<major>.<minor>.<patch>-nightly.<n>`, each number 1 to 9 ASCII digits,
  compared by value (leading zeros don't count). A nightly sorts after the previous stable and before its own stable.
  `ardia_update_compare_versions` writes -1, 0 or 1. A version over 64 bytes or not UTF-8 is `VERSION`, unread.
- `ardia_update_check_offer` is `OK` when the candidate is newer than the installed version and the channel takes it:
  stable takes stable versions only, nightly takes both (`CHANNEL`, `NOT_NEWER`, `VERSION`). A downgrade, the same
  version again, or a nightly of the installed stable is never offered.
- Pointer rules are the same as `ardia_core`'s: a `NULL` input with length 0 is empty, with any other length it is
  `INVALID_ARGUMENT`, and a length check that refuses an input wins over a `NULL` pointer. An output slot only has to
  be aligned and writable: it may be uninitialized, since every call writes it (its result, or zeroes on a refusal)
  and none reads it. No call allocates, temporarily or otherwise (`tests/no_allocation.rs` counts every allocation
  across the vectors), so there is nothing to free, and the library keeps no state.

Ed25519 goes through `ardia-crypto`'s backend, RustCrypto under cargo and BoringSSL in Chromium.
`tests/boringssl/check.sh` builds the same `ardia-crypto` and `ardia-update-core` sources against a pinned BoringSSL
release under cargo and runs the crypto known answers and every update vector through the BoringSSL backend. It refuses small-order
keys and `R` values and a non-canonical `S`. OpenSSL, which the helper uses, accepts a small-order key's trivial
signature; that can't matter for a release, since installs pin `scripts/linux/linux-update.pem`, but it's recorded.

`tests/update-vectors.json` holds the shared vectors (`ARDIA_WRITE_UPDATE_VECTORS=1 cargo test -p ardia-update-core
--test vectors` regenerates them from fixed test keys, and fails when they drift). Each manifest case records the full
`outcome`, the unsigned `parse` the engine does before downloading, whether the signature verifies, and, where another
implementation answers differently, that implementation's answer (`linuxPolicy`, `helper`, `openssl`).
`tests/linux-update/test_linux_update.py` runs them against the engine's `ac_linux_self_update_policy.h`, the root
helper's own bash functions, `openssl pkeyutl -verify -rawin`, Node's `crypto.verify` (which `sign-update.mjs` signs
with) and the version rules in `apps/desktop/src/platform/linux/updateReleases.ts` and `apps/browser/src/lib/versions.ts`.

## Chromium bookmarks import: `ardia_import`

`include/ardia_import.h` is generated by cbindgen (`ARDIA_WRITE_HEADER=1 cargo test -p ardia-import-ffi --test header`)
from `crates/ardia-import-ffi`, which builds `libardia_import` (static and shared). It is a separate library from
`libardia_core` so no engine copies it until a host switches: nothing under `engine/` or in `copies.tsv` reads it, and
the macOS, Linux and Windows engine keys don't move. Every name in it starts with `ardia_import_` or `ARDIA_IMPORT_`,
so it can share a translation unit with `ardia_core.h` (`tests/c/import_smoke.c` includes both). A final link holds one
Rust archive, so a host links `libardia_import` or `libardia_core`, not both, until they are merged into one. The
libraries export exactly the 3 functions the header declares (`tests/check_exports.py`).

### What the caller must guarantee

- `bookmarks` and `account_bookmarks` are `NULL` or point to an `ardia_import_bytes` whose `len` is readable. Its
  `ptr` is read only when `len` is from 1 to `ARDIA_IMPORT_MAX_INPUT_BYTES`, so it may be left uninitialized
  otherwise; in that range it points to `len` bytes that stay readable and unchanged for the whole call.
- `out` is `NULL` or points to aligned, writable memory for one `ardia_import_buf` that nothing else touches during the
  call. The library only writes it and never reads it, so uninitialized memory is fine. A buffer the slot held before
  is not freed: free it first or it leaks.
- A buffer the library wrote keeps its `ptr` and `len` unchanged until it goes back to `ardia_import_buf_free`, and
  goes back exactly once.

### What the library checks

- A `NULL` `out` returns `ARDIA_IMPORT_STATUS_INVALID_ARGUMENT` and writes nothing.
- A `NULL` file pointer is a file the profile doesn't have. `{NULL, 0}` or any zero length is a file that is there and
  empty, which is unreadable JSON. A `NULL` `ptr` with a length from 1 to the cap returns
  `ARDIA_IMPORT_STATUS_INVALID_ARGUMENT`.
- `len` is read first. A length over `ARDIA_IMPORT_MAX_INPUT_BYTES` (64 MiB, Linux's and Windows' cap today) or of 0
  is decided without reading `ptr`. For `bookmarks` it returns `ARDIA_IMPORT_STATUS_TOO_LARGE`; an oversized `account_bookmarks` is skipped like
  an unreadable one.

### Results

- `ardia_import_chromium_bookmarks` reads a Chromium profile's `Bookmarks` and `AccountBookmarks` (Chrome, Edge,
  Brave, Arc, Dia, Vivaldi, Opera, Helium) and writes the `bookmarks` field of the existing `ImportResult`: a folder
  titled `Bookmarks` whose children are the non-empty `bookmark_bar`, `other` and `synced` roots with `role`
  `toolbar`, `other` and `mobile`. Nodes carry `type`, `title`, `url` (links), `children` (folders), `dateAdded`
  (milliseconds since 1970, when known) and `role` (roots). An `AccountBookmarks` root's children join the root with
  the same role; a new role goes last.
- `ARDIA_IMPORT_STATUS_OK` is the only success. Every other status except a `NULL` `out` writes `{"code": "..."}`:
  `notFound` (neither file), `unreadable` (`Bookmarks` isn't Chromium bookmarks JSON; a bad `AccountBookmarks` is
  ignored), `tooLarge` or `argument`. The JSON never echoes input.
- `ardia_import_buf_free(&buf)` zeroes the bytes, frees them and writes `{NULL, 0}` back. `NULL` or an empty slot does
  nothing. The library keeps no globals, starts no threads and makes no system calls besides allocation.

### Parsing rules and where hosts differ today

`tests/import-bookmarks-vectors.json` holds the shared cases. Rust's answer is `expect`; `platforms` records where the
Mac's Swift, the Windows TypeScript and the Linux C++ answer differently today, so each host switch states which inputs
change. `tests/import-bookmarks/test_import_bookmarks.py` runs the Swift and TypeScript parsers against their recorded
answers in CI on macOS; the Linux answers are read from its source. Rust:

- parses RFC 8259 JSON as UTF-8 after one optional UTF-8 BOM (a second one is unreadable), with at most 200 nested arrays and objects, like
  Chromium's own `base::JSONReader`. Invalid UTF-8, lone surrogate escapes, trailing commas, comments and numbers out of
  double range are unreadable. A repeated key keeps its last value.
- keeps every link with a non-empty string `url`, whatever its scheme (bookmarklets are a feature), and every folder.
  A missing or non-string `name` is an empty title; an empty root name takes the default (`Bookmarks Bar`,
  `Other Bookmarks`, `Mobile Bookmarks`). Other `type`s and children that aren't objects are skipped one by one.
- reads folders 64 levels below a root, as Linux does, and keeps a folder at the cap empty. At most 250,000 nodes come
  back across both files: each folder takes its slot before its children are read, so the cap is a hard ceiling. Linux
  counts a folder after its children and returns up to one extra node per open folder.
- reads `date_added` as a string holding an optionally signed 64-bit integer of microseconds since 1601, like Swift,
  and keeps it only after 1970, like Linux.

The output nests at most 132 JSON levels, under Chromium's, Swift's and JavaScript's parser limits.
