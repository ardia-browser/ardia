# 0.2.46 → 0.2.47 release gate

0.2.47 collects the 0.2.47 nightlies. It is cut at 8aaf967f2, which reverts #2970's display link (#3226), because the display link stopped JS timers while the display slept. The candidate is the local signed, notarized and stapled `scripts/release.sh 0.2.47` build (build 127, e4e08931c). The control is the published 0.2.46. 0.2.46 is native API 58 and 0.2.47 is 87, so each app ran its own bench bundle. Measured on 2026-11-20 on the Mac mini, interleaved, holding the perflab lock. cpu-cap wasn't running there, so no run was paused.

**Result: passes, read pooled over three interleaved rounds.** The mini was intermittently busy: mediaanalysisd, which analyses the photo library, ran at about 120 % at the start of rounds 1 and 2 and at the end of round 3. So no single round counts as quiet. Read one round at a time, "ranges separate" fired on a different timing row in each round, never the same row twice, and each by a hair:
- round 1: idle CPU at 20 tabs, all processes;
- round 2: idle CPU at 1 tab, and new window on screen;
- round 3: new tab first paint, 83–83 against 84–86.

The release coordinator ruled that the gate is read pooled over all three rounds. A row fails only if:
- the pooled ranges separate, or
- 0.2.47 is worse in all three rounds and its pooled median is worse by more than 0.2.46's own round-to-round spread.

No row fails. The per-round tables are kept below.

**What to watch:** launch read slower in all three rounds:
- window shown: +12, +12.5, +3.5 ms, pooled 343 → 356 ms;
- with content: pooled 457 → 474 ms;
- JS running: pooled 413 → 429 ms.

That is 3–4 %, inside 0.2.46's own 40–48 ms round-to-round spread, so it passes the rule. It is still the most consistent difference here and the first row to look at in 0.2.48. New window is also 2–4 ms slower in every round, inside a 4.5–5.4 ms spread. Memory is about +3 to +12 MB at 20 tabs, which the owner accepted for this release.

## Follow-up: is the launch difference real? (2026-11-22)

**Verdict: real but small, about 10 ms, and below what a bisect can pin down.** No code changes for it. Watch `perf_launch`'s phase fields (`engine_ms`, `rn_ms`, `js_ms`, `commit_ms`) in 0.2.48 rather than chase it now.

**Field, warm launches only** (`cold` not `true`, `first_of_version = false`, production, last 30 days). Unmatched medians make 0.2.47 look faster. 0.2.46 has 6,979 launches from 1,770 copies, and 0.2.47 has 1,232 from 473. Content on screen reads 1048 → 933 ms. That is the cohort mix: 0.2.47's early adopters aren't 0.2.46's population. The one phase that moved the other way is `commit_ms − js_ms`, 116 → 140 ms.

Matched per copy (207 copies with warm launches on both versions; the median of each copy's own difference):

| phase | Δ (0.2.47 − 0.2.46) |
|---|---|
| `rn_ms` (React Native starts loading) | +23 ms |
| `engine_ms` | +12 ms |
| `js_ms − rn_ms` (bundle load) | +4 ms |
| `commit_ms − js_ms` (JS to the first commit) | +11 ms |
| `content_ms` | +32 ms (IQR −158 to +330) |
| `tab_paint_ms` | +56 ms |

Matched copies also carry calendar drift: their sessions and histories grew between the two versions. So +32 ms is an upper bound.

**Lab, Mac mini, perflab lock, one-tab session.** Each release ran its own published bundle with the perf probe on. Marks were counted from process start, and each build's first (cold) launch was dropped. Builds were interleaved round-robin, and the Δ is the median of paired differences against 0.2.46.

| round | pairs | Δ bundle start (native) | Δ bundle evaluation | Δ bundle end → first commit | Δ first window |
|---|---|---|---|---|---|
| 1: 0.2.46 vs 0.2.47 | 9 | +6 | +4 | +1 | **+9** |
| 2: 0.2.46, nightly.1–9 (no 3), 0.2.47 | 9 | +7 | +9 | +28 | **+34** |
| 3: 0.2.46, nightly.4, nightly.5, 0.2.47 | 12 | −15 | +7 | −2 | **+7** |

0.2.47 is slower to the first window in all three rounds, by 7 to 34 ms, the same sign as the gate's +13 to +16 ms. Round 2 put a step between nightly.4 (+5) and nightly.5 (+27). That range is 166 commits and includes an engine change (windowless page screen rects, video upscaling). Round 3 repeated those builds alone and found no step: nightly.4 −7, nightly.5 −12. Meanwhile 0.2.46's own bundle end → first commit moved from 87 to 123 ms between rounds. Run-to-run noise is larger than the effect, so a nightly bisect can't place it. A commit bisect would need an engine build per step, and each would still be under that noise.

The JS bundle grew from 7.7 to 10.0 MB (+29 %), but bundle load and evaluation account for only +4 to +9 ms of it.
