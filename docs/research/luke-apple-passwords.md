- Nothing Luke has written, merged or open, talks to Apple's helper (`com.apple.passwordmanager`) directly, and none of it implements SRP pairing. Our helper route is not duplicated by anyone. The one thing that could change its premise is #2943 (open, Luke), which would run Chromium extensions, possibly including Apple's, in WebKit tabs (section 5).

## 3. What is in main today, end to end

**Chromium tabs, the extension route [verified].**
1. Apple's iCloud Passwords extension is installed by the user from the Chrome Web Store. Apple's helper `PasswordManagerBrowserExtensionHelper` only starts when its parent holds `com.apple.developer.web-browser.public-key-credential` or is one of about 40 named browsers; Apple granted the entitlement to `com.ardia.browser` (`docs/dia-feature-parity.md:564`; #3368 body; `scripts/release/export-sign.sh:14` signs with `Ardia-ICloudPasskeys.entitlements` when the profile grants it).
2. `ArdiaNativeMessaging.mm` copies Apple's manifest from `/Library/Google/Chrome/NativeMessagingHosts` into the profile; the engine patch makes the host findable only in an entitled build. Debug, train and ad hoc builds never start the helper (patch header lines 1-7).
3. macOS then asks to "Enable Password AutoFill for 'Ardia'" and the extension shows its own pairing code (#3368 verification; release note `docs/release-notes/0.2.48.md:9`). Issues #18 (closed 2026-11-22) and #1562 (closed 2026-11-24) were closed as fixed by this.
4. Not verified by a person: #3368's "Still needed": the owner entering the pairing code and checking a fill with a signed-in iCloud Keychain. #4236 and #4237 (open) ask for diagnostics because a failed host check is silent.
5. Telemetry exists for it: `extension_installed` with `icloud_passwords` and `apple_helper_allowed`, where "allowed" is `getPasskeyAccess().entitled` (`extensionInstalls.ts:28-31`).

**How a user turns it on today:** install the extension from the Web Store in a signed release. There is no Settings switch. Settings › Profiles › Passwords › Password manager lists Ardia, None and any enabled password-manager plugin (`docs/plugins.md:901`); none ships (`:910`).

**Chromium tabs, the plugin route [verified].** Everything #2841 built is still there and dormant: the `passwordManager` plugin contribution, `passwords.setFieldProviders/showSystemPanel/setUpVerificationCode`, the key in login and code fields, Edit › AutoFill › Passwords…, the otpauth offer and the offer-to-save record. Only the official "Apple Passwords" plugin was removed (#3367, `29fbe6c97`), and 0.2.47 users who had picked it were moved back to Ardia. A third-party plugin could still turn it on.

**WebKit tabs [verified].**
- Login list: Luke's #2941 (`53df2dd82`) fills from Chrome's saved passwords through `ac_passwords_page_*`, with a native dropdown (`WebKitAutofillDropdown.swift`, `WebKitLogins.swift`), save after a settled sign-in (`WebKitAutofill+Save.swift`), and a gate: `WebKitPasswordGate.verdict` returns `.leftToManager` when `ArdiaWebView.fieldProvider(profile:)` is non-nil (`WebKitPasswordGate.swift:17`, `WebKitLogins.swift:186`), counted as `webkit_passwords_left_to_manager`.
- Field-provider key and otpauth offers work in WebKit pages through `WebKitTab+FieldProviders.swift`, but only with a plugin provider, so nothing today.
- The iCloud Passwords extension does not run in WebKit tabs: `WebKitExtension*` does not exist in main (`ls packages/ardiacore/ios`); it is #2943, open and conflicting.
- Passkeys are separate (v0.2.48: iCloud Keychain passkeys through the same entitlement).
